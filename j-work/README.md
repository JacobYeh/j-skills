## 四、当前挑战与应对策略

### Peer 问题（核心痛点）

**问题表现：**
- 情绪不稳定，消极状态
- 被本地管理层不满，综合反馈不佳
- 行动力弱、不稳定、散漫
- 不愿意参与本地 hands-on 工作

**但实际情况：**
- 积极跨时区参与 global 项目
- 与美国 leader 牵线，被欣赏
- 这种"被欣赏"反而让本地问题更难处理

**你的优势视角：**
> Peer 的问题反而能衬托出你的优点——稳定、积极、执行力强

**应对策略：**
1. 保持自己的稳定性和积极性，不被对方影响
2. 在 global 面前展现高执行力和人际把控能力
3. 用行动证明自己，而不是对抗

---

### 本地基础设施痛点

**历史遗留问题：**
| 问题 | 说明 | 重要性 |
|---|---|---|
| **电源插座不稳定** | 老化、接触不良 | 高 |
| **网口不稳定** | 影响网络连接 | 高 |
| **桌子移动/布局** | 变更频繁，需重新规划 | 高 |
| **空调项目复杂** | 多个vendor，历史问题多 | 中 |
| **基建项目理清** | 需要与 vendor 强执行 | 中 |

**目标（短期）：**
- 理清本地基建项目历史问题
- 与 vendor 强执行，推进改善
- 在 global 面前展现高项目执行力

## 七、核心故事库（STAR格式，面试必用）

### 故事1：Bloomberg交易软件故障 ⭐最最强
**情境：** 周五中午，MD用户无法访问Bloomberg，30分钟后要赶飞机。
**做法：**
1. 先安抚用户，同时让用户助理登录备用PC（可行但VPN不行）
2. 设置远程桌面快捷方式，让用户先能操作
3. 用户离开后，排查范围——发现所有DA laptop都受影响
4. 用Process Monitor + NetMon重现问题
5. 确认为新版本BB不兼容，提交紧急change request降级
6. 起草邮件描述经过，抄送MD

**关键点：** 压力下先给workaround再修根因，系统性思维

---

### 故事2：OpenAFS/WinAurora交易系统宕机（S2，5小时）
**情境：** 夜间值班，NA地区20+交易员无法访问多个应用。
**做法：**
1. 和eng团队一起排查3小时，发现根因：系统LDAP retry次数硬编码为3次
2. 需要紧急权限提升 → 联系security团队的ED
3. 完成修复后复盘：分配全球各区域SME、建立自动恢复脚本、改善权限管理
4. 设立月度会议审查机制

**关键点：** 跨团队协作、事后系统性改进、不只是修复问题而是预防

---

### 故事3：MultiLogonUI.exe（Citrix XenDesktop登录异常）
**情境：** 多台开发人员电脑登录时间10分钟+，L2一直在换硬件。
**做法：**
1. 追踪到MultiLogonUI.exe由摄像头驱动产生
2. 发现规律：机器能RDP但无法物理登录
3. 给出修复方案而非简单重建
4. 节省了不必要的硬件替换

**关键点：** 诊断根因 vs 治标

---

### 故事4：Zscaler中国部署（从不可能到可能）
**情境：** 中国大陆用户无论在办公室还是外部都无法通过Zscaler访问内网。
**做法：**
1. 协调Zscaler vendor启用大陆节点
2. 优化PAC proxy file以符合中国法规
3. 与legal、网络团队跨部门协作
4. 给用户提供ZDX培训

**关键点：** 项目管理、跨vendor协调、escalation to higher management

---

### 故事5：Morgan Stanley虚拟化项目（30-40用户）
**情境：** 为30-40位高级管理人员做桌面虚拟化，让其能在任何地方工作。
**挑战：** 用户抱怨VM慢、不稳定、部分应用不可用（网络环境差异大）
**做法：**
1. Daily catch-up与用户保持沟通
2. 主导与Microsoft/Citrix vendor的troubleshooting session
3. 一个一个解决问题，最终效果超出用户预期

---

### 故事6：Kohler亚洲资产管理系统（0到1）
**情境：** 亚洲各站点各自独立的资产系统，难以跟踪采购需求和更新计划。
**做法：**
1. 主导与SAP团队、IT infra、sourcing、finance的跨部门项目
2. 设计web-based集中系统
3. 最终产出：综合报告展示资产、采购、vendor状态
4. 实现了亚洲区资产集中管理

**关键点：** 这个故事特别适合展示"理清历史遗留问题 + vendor协调 + 项目执行力"

---

### 故事7：与同事冲突后和解
**情境：** app team lead要求把所有机器退出域（GPO strict，日常admin清理会影响他们的应用），发生争执。
**结果：** 5分钟后他回来请你喝咖啡，邀你去打羽毛球，逐一解决问题。
**教训：** 不要当场拒绝，保持baseline，理解对方真实需求。

---

### 故事8：犯了错误——Outlook远程重启
**情境：** 远程用户（在东京）没回复消息，直接跑了修复命令，10分钟后问题解决但用户不满（因为Outlook被重启）。
**教训：** 必须先得到对方确认才能执行可能影响用户的操作。

### Q: 你最大的优势是什么？

## 九、技术知识速查

### OSI七层排错框架

| 层级 | 检查什么 | 常用命令 |
|---|---|---|
| 物理层 | 网线接好？设备通电？ | 眼观 |
| 数据链路层 | 速率匹配？MAC冲突？ | - |
| 网络层 | IP正确？子网掩码？网关？DHCP？ | ipconfig, ping |
| 传输层 | 防火墙？端口开放？ | Test-NetConnection |
| 会话/表示/应用层 | 软件设置、代理 | - |

### Active Directory核心概念
- **LDAP**：用于在域中查找设备/用户
- **Kerberos**：用于用户登录认证
- **GPO**：组策略对象
- **OU**：组织单位

### DNS/DHCP（弱点，需加强）
- DHCP租约过程
- DNS记录类型（A/AAAA/CNAME/MX）
- 两者关系：DHCP动态分配IP，DNS解析名称到IP

### PowerShell Remote
```powershell
Invoke-Command -ComputerName $servers -ScriptBlock { Restart-Service Spooler }
```
要求：WinRM启用，管理权限，端口5985/5986

### 网络命令
- `ipconfig /all` — 查看IP、网关、DNS
- `ping` — 连通性测试
- `tracert` — 路由追踪
- `nslookup` — DNS查询
- `Test-NetConnection -Port 443` — 端口测试

## 十、工作场景指南

### 场景1：紧急故障（交易员无法工作）
```
1. 确认影响范围（几个人？哪个地区？）
2. 给出临时workaround（让用户能继续操作）
3. 远程诊断
4. 修复根因
5. 通知用户和manager
6. 写incident report
7. 复盘：下次怎么预防？
```

### 场景2：与消极的peer合作
**原则：不被对方影响，用行动证明自己**
- 保持稳定性和积极性
- 不公开抱怨，私下与manager沟通
- 用高质量输出赢得信任
- 主动承担 hands-on 工作

### 场景3：历史遗留问题（vendor协调）
**原则：理清 + 执行 + 记录**
1. 审计现状，列出所有问题点
2. 明确责任 vendor
3. 制定改善计划和时间表
4. 强执行，跟进到底
5. 记录进展，向 global 汇报

### 场景4：新系统/项目上线
```
1. 明确需求（internal vs external、多少人、内容类型）
2. 设计架构（AD验证、server角色、防火墙、load balance）
3. 协调资源（vendor、跨团队）
4. 分阶段执行
5. 用户培训+文档
6. 复盘优化
```

### 场景5：优先级判断
1. 先做影响大的（交易员 > 普通员工）
2. 能rollback的先做（控制风险）
3. 复杂的拆成多个小任务
4. 保持沟通

### 场景6：跨时区协作
**原则：清晰Agenda + 高质量输出 + 主动汇报**
- 会议前准备清晰议程
- 会议中高参与、有贡献
- 会议后总结、跟进
- 主动与美国 leader 保持联系
